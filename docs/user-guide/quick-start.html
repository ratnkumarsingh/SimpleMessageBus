1. The idea in one page

A producer is an app that sends messages. A consumer is an app that receives them. They never talk to each other directly. The broker sits in the middle: it stores every message safely and hands it to each consumer that wants it.

The producer sends one message to a topic. The broker makes one copy for every subscription on that topic. Each consumer owns a subscription and gets its own copy in one of three ways: the broker pushes it over SignalR, the broker calls the consumer's web address (Webhook), or the consumer asks for it (Pull with long polling).

Words you will see

WordMeaning
TopicA named channel for one kind of news, for example payments. Producers send to a topic.
MessageWhat the producer sends: a type name (like PaymentProcessed.v1) and a JSON payload with the data.
SubscriptionA consumer's "mailbox" on a topic. Every subscription gets its own copy of every message.
DeliveryOne copy of a message, on its way to one subscription.
ACK"Done, thank you." The consumer tells the broker the delivery was handled. It will not come again.
NACK"It failed, try again later." The broker waits a little and delivers it again.
Lease (lock)The time a consumer has to finish a delivery. If it does not answer in time, the broker gives the delivery out again.
Dead-letter queue (DLQ)Where a message goes when it failed too many times or the consumer said "this can never work". Nothing is lost; the admin can look at it and send it again.
API keyYour app's password for the broker. Every call carries it.
Good to know: the broker may sometimes deliver the same message twice (for example after a network error). This is normal. Every consumer must be able to handle a repeat safely (see chapter 4).

2. Before you start: ask the admin

You do not create topics, keys or subscriptions yourself. The broker admin does that for you. Tell the admin what your app is, and you will get back what you need:

You are…Tell the adminYou get back
ProducerYour app's name and which topic you want to send to.An API key and the topic name.
Consumer · SignalRYour app's name, the topic, and "SignalR mode".An API key and a subscription ID (a GUID).
Consumer · WebhookYour app's name, the topic, "Webhook mode", and your HTTPS address, for example https://billing.internal/webhooks/payments.An API key, a subscription ID and a webhook secret (used to check that calls really come from the broker).
Consumer · PullYour app's name, the topic, and "Pull mode".An API key and a subscription ID.

You also need the broker's address, for example https://broker.internal/.

Keep secrets secret. The API key and the webhook secret are shown only once. Put them in your secret store (Key Vault, environment settings). Never put them in source code or Git, and never write them to logs.

Add the client package (all apps)

.NET apps use the MessageBroker.Contracts package. It has the ready-made client, the SignalR listener and the webhook signature checker. Add it to your project, then put the broker settings in configuration:

// appsettings.json (the key itself comes from your secret store)
"Broker": { "Url": "https://broker.internal/", "ApiKey": "<from secret store>" }

3. Producer: how to send a message

Sending is one HTTP call. The broker answers only after the message is safely stored.

Step 1Register the broker client

In Program.cs, register BrokerClient with the broker address and your API key.

builder.Services.AddBrokerClient(o =>
{
    o.BaseAddress = new Uri(builder.Configuration["Broker:Url"]!);
    o.ApiKey      = builder.Configuration["Broker:ApiKey"]!;
});
Step 2Build the message

Give it a type name with a version (PaymentProcessed.v1) and put your data in the payload. Keep it small (under 256 KB) and do not put passwords or secrets in it. The correlation ID is optional: use your order or request ID so the whole flow can be traced later.

var request = new PublishRequest
{
    MessageType   = "PaymentProcessed.v1",
    CorrelationId = payment.OrderId,
    Payload       = JsonSerializer.SerializeToElement(
                        new { payment.PaymentId, payment.Amount })
};
Step 3Send it, with an idempotency key

The idempotency key is a name for this business event, for example payment-PAY-123-processed. If you send the same key twice, the broker keeps only the first one. So you can safely send again after an error without making a duplicate.

var result = await broker.PublishAsync("payments", request,
    idempotencyKey: $"payment-{payment.PaymentId}-processed", ct: ct);

// result.MessageId     → the new message's ID (log it for tracing)
// result.IsDuplicate   → true if this key was already sent before (still OK)
Step 4Look at the answer
AnswerWhat it means → what you do
201 CreatedStored. You are done.
200 OKAlready sent earlier with this key. Treat it as success.
400 / 413The message is wrong or too big. Fix it. Do not just send it again.
401 / 403 / 404Wrong key, no permission, or no such topic. Check your settings or ask the admin.
503, timeout, network errorThe broker is busy or down. Try again later with the same key (wait 1, 2, 4, 8… seconds).

With the .NET client, errors arrive as BrokerApiException. Its IsTransient property is true when it is safe to try again.

Do

  • Always send an idempotency key.
  • Retry only on 503, timeouts and network errors.
  • Put a version in the type name (.v1, .v2).
  • Save the message in your own database first (an "outbox" table) if losing it would be bad.

Don't

  • Don't retry 4xx errors unchanged.
  • Don't put secrets or large files in the payload.
  • Don't log your API key.
  • Don't expect consumers to get messages in exact order.

4. Rules for every consumer

Whatever way you choose to receive (SignalR, Webhook or Pull), follow these five rules.

  1. Be ready for repeats. The same message can arrive twice. Save the messageId of every message you have handled (in your database, in the same transaction as your work). If you see it again, just say "done" (ACK) and do nothing else.
  2. Say "done" only after your work is saved. If you ACK first and then crash, the message is lost for you.
  3. Answer in time. Each delivery has a deadline, lockedUntil. After it, the broker thinks you failed and sends the delivery again. For long work, ask for more time (renew).
  4. NACK to try again, dead-letter to give up. A temporary problem (database busy, other service down)? NACK, and the broker tries again later. A message that can never work (bad data, unknown type)? NACK with dead-letter, and it goes straight to the DLQ.
  5. Never log the payload or keys. Log messageId, correlationId and deliveryId instead.

What a delivery looks like

All three ways give you the same JSON:

{
  "deliveryId":  81234,                                   ← used to ACK / NACK / renew
  "lockToken":   "2c9a0f4e-5d71-4b0e-9b77-0c4b9a2f1e11",   ← proves this delivery is yours right now
  "lockedUntil": "2026-10-08T12:31:05Z",                  ← answer before this time (UTC)
  "attempt":     1,                                       ← 1 the first time, 2 the second time, …
  "message": {
    "messageId":     "01a11b48-b86f-784f-a72d-8e1bc7526202",  ← check this for repeats
    "messageType":   "PaymentProcessed.v1",
    "correlationId": "ORDER-48213",
    "createdAt":     "2026-10-08T12:30:04Z",
    "payload":       { "paymentId": "PAY-12345", "amount": 1500.00 }
  }
}

How many times does the broker try?

By default, 4 times, waiting about 30 s, then 60 s, then 120 s between tries. After the last failed try, the message goes to the DLQ. If your app may be down for longer, ask the admin to give your subscription more tries.

5. Consumer with SignalR

Choose SignalR when your app cannot offer a web address the broker can call (desktop app, behind a firewall, Blazor Server), or you want messages instantly. Your app opens one connection to the broker and keeps it open; the broker pushes each message down that connection.
Step 1Get your details from the admin

You need the broker address, your API key and your subscription ID.

Step 2Write the handler: what to do with one message

Return DeliveryResult.Ack when the work is saved. Return DeliveryResult.Fail(...) to try again later, or add deadLetter: true to give up on it. If your code throws an exception, that counts as "try again".

async Task<DeliveryResult> HandleAsync(Delivery delivery, CancellationToken ct)
{
    var type = delivery.Message.MessageType;
    if (type != "PaymentProcessed.v1")
        return DeliveryResult.Fail("UnknownType", type, deadLetter: true);   // give up

    await ProcessOnceAsync(delivery, ct);       // your work (skips repeats)
    return DeliveryResult.Ack;                  // done
}
Step 3Create the listener and start it

SignalRDeliveryListener connects, signs in with your key, listens on your subscription, and sends ACK or NACK for you based on your handler's answer. Run it in a BackgroundService so it lives as long as your app.

public sealed class PaymentListener(IConfiguration config) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stop)
    {
        var brokerUrl      = new Uri(config["Broker:Url"]!);
        var subscriptionId = Guid.Parse(config["Broker:SubscriptionId"]!);

        await using var listener =
            new SignalRDeliveryListener(brokerUrl, config["Broker:ApiKey"]!, HandleAsync);

        await listener.StartAsync([subscriptionId], stop);
        await Task.Delay(Timeout.Infinite, stop);    // keep listening until the app stops
    }
}
// Program.cs:  builder.Services.AddHostedService<PaymentListener>();
Step 4Nothing else: it reconnects by itself

If the network drops or the broker restarts, the listener reconnects on its own. Unanswered deliveries come again after their deadline, which is safe because you skip repeats. For long work, call listener.RenewAsync(delivery) to get more time.

Not .NET? Any SignalR client works: connect to https://<broker>/hubs/deliveries with your API key as the access token, call Subscribe(subscriptionId), handle the Deliver event, then call Ack or Nack.

6. Consumer with Webhook

Choose Webhook when your app is a web service that already has an HTTPS address. You do not keep any connection open: the broker calls you with an HTTP POST for every message, and your HTTP answer tells it whether it worked.
Step 1Make an HTTPS endpoint and give its address to the admin

For example https://billing.internal/webhooks/payments. It must use HTTPS. The admin creates your subscription with this address and gives you your webhook secret.

Step 2Check that the call really comes from the broker

Every call is signed with your webhook secret. Read the body as plain text first, then check it with WebhookSignature.Verify. If the check fails, answer 401 and do nothing.

Step 3Do the work, then answer
You answerThe broker understands
200 (any 2xx except 202)Done (ACK).
4xx or 5xxFailed, try again later (NACK).
202 Accepted"I took it and will report back myself." Use it for long work, or to give up on a message: later call POST /api/v1/deliveries/{id}/ack, or /nack with "deadLetter": true. The ID and lock token are in the X-Broker-Delivery-Id and X-Broker-Lock-Token headers.
No answer within 30 sFailed (timeout), try again later.

The whole endpoint:

string[] secrets = [builder.Configuration["Broker:WebhookSecret"]!];

app.MapPost("/webhooks/payments", async (HttpRequest request, PaymentHandler handler) =>
{
    using var reader = new StreamReader(request.Body);
    var body = await reader.ReadToEndAsync();                 // 1. read the raw text first

    var signature = request.Headers[WebhookHeaders.Signature];
    var timestamp = request.Headers[WebhookHeaders.Timestamp];
    if (!WebhookSignature.Verify(signature, timestamp, body, DateTimeOffset.UtcNow, secrets))
        return Results.Unauthorized();                        // 2. not from the broker

    var delivery = JsonSerializer.Deserialize<Delivery>(body, JsonSerializerOptions.Web)!;
    try
    {
        await handler.ProcessOnceAsync(delivery);             // 3. your work (skips repeats)
        return Results.Ok();                                  //    → done (ACK)
    }
    catch (Exception)
    {
        return Results.StatusCode(503);                       //    → try again later
    }
});
Good to know: after 5 failures in a row, the broker stops calling you for 60 seconds; messages wait safely meanwhile. When the admin changes your secret, the old and new ones both work for 24 hours: put both in secrets during that time.

7. Consumer with Long polling (Pull)

Choose Pull when you want to decide yourself when and how fast to take messages: background workers, batch jobs, or work you want to spread over several copies of your app. Your app asks the broker for messages in a loop.

What is long polling? Your app asks "any messages?" and the broker waits (up to 20 seconds here) before answering. As soon as a message arrives, the answer comes back at once. If nothing arrives, you get an empty list and simply ask again. So your app reacts instantly, but does not flood the broker with questions.

Step 1Get your details from the admin

You need the broker address, your API key and your subscription ID. Register BrokerClient as in chapter 3, step 1.

Step 2Ask for messages in a loop

Call ReceiveAsync with how many messages you want at most (1–32) and how long to wait (0–30 s; use 10–30).

Step 3Handle each message and answer for each one

Every message in the batch has its own deadline. Call AckAsync when the work is saved, or NackAsync to try again later (add deadLetter: true to give up). For long work, call RenewAsync to get more time.

The whole worker:

public sealed class PaymentWorker(BrokerClient broker, IConfiguration config) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stop)
    {
        var subscriptionId = Guid.Parse(config["Broker:SubscriptionId"]!);
        while (!stop.IsCancellationRequested)
        {
            IReadOnlyList<Delivery> batch;
            try
            {
                // waits up to 20 s, returns at once when a message arrives
                batch = await broker.ReceiveAsync(subscriptionId,
                    maxMessages: 16, waitSeconds: 20, ct: stop);
            }
            catch (BrokerApiException ex) when (ex.IsTransient)
            {
                await Task.Delay(5000, stop);           // broker busy: wait, then ask again
                continue;
            }

            foreach (var delivery in batch)
                await HandleAsync(delivery, stop);
        }
    }

    async Task HandleAsync(Delivery delivery, CancellationToken stop)
    {
        try
        {
            await ProcessOnceAsync(delivery, stop);     // your work (skips repeats)
            await broker.AckAsync(delivery, stop);      // done
        }
        catch (InvalidDataException ex)                 // bad data: give up
        {
            await broker.NackAsync(delivery, "Invalid", ex.Message, deadLetter: true, ct: stop);
        }
        catch (BrokerApiException ex) when (ex.IsLeaseLost)
        {
            // too late: it will come again, and the repeat check handles it
        }
        catch (Exception ex)                            // other problem: try again later
        {
            await broker.NackAsync(delivery, "Error", ex.Message, ct: stop);
        }
    }
}
Need more speed? Run more copies of the worker. Each message is given to only one of them at a time.

Not sure? If you are a web API, pick Webhook. If you cannot be called from outside, pick SignalR. If you want full control over speed, pick Pull.

9. When something goes wrong

You seeWhat to do
401 UnauthorizedYour API key is missing, wrong or expired. Check your settings; ask the admin for a new key if needed.
403 ForbiddenYour key is fine, but you are not allowed to use this topic or subscription. Ask the admin.
404 Not FoundThe topic name or subscription ID is wrong. Check the spelling and the ID.
410 Gone on ACK / NACKYou answered after the deadline. Do nothing: the message comes again and your repeat check handles it. If it happens often, your work is too slow; renew, or ask the admin for a longer lease.
503 Service UnavailableThe broker is busy or restarting. Wait a few seconds and try again.
Webhook: no calls arriveIs your HTTPS endpoint reachable, and does it answer 2xx? Does the signature check use the right secret? After 5 failures in a row the broker pauses calls for 60 s.
Messages in the DLQLook at the error saved with each message (admin dashboard, or ask the admin). Fix the cause, then ask the admin to send the messages again.
